The DEBUG panel, operable

A working mock of the proposed floating debugger: drag it by the grip, scrub the slider, and watch the projectile plot redraw one frame per loop iteration. The chrome around it is a facsimile of the Pyodide embed; the panel is the actual proposal.

SUPERSEDED 2026-09-08 — this is the pre-build proposal, not the shipped panel. Slice 1 is built on feature/debug-panel behind features.debugPanel, and it diverges from this specimen in three ways that matter: (1) the transport is a 2×2 grid of three captioned boxes (STEP MODE / AUTO MODE / BREAKPOINTS), not the single row shown here; (2) AUTO MODE is a forward-only ladder of five fixed rates — 1/5, 1/2, play, 2, 5 lines per second, the slow two drawn as stacked fractions — and backwards autoplay was deleted; (3) autoplay stops at breakpoints (debugAutoStep advances one step, then tests where it landed), which the autoplay demonstrated below deliberately ignores. Also shipped and not shown here: no message of any kind renders inside the pill — they all go to the top of the floating variables window. Keep this file for the interaction argument it makes; do not read geometry or behaviour off it.

What is real here, and what is faked

So nobody has to guess which parts are claims about the implementation.

Real — behaves as the build would

The recording is a genuine trace: 34 loop iterations of the program on the left, one step per executed line, 491 steps and 34 captured frames. Stepping is a walk over a finished array, exactly as record & replay works today.

Frames are sparse against steps — captured only where plt.plot runs, which is the fig.stale policy in miniature. The plot shows the newest frame at or before the current step, so scrubbing backwards un-draws the trajectory.

Console output is revealed by recorded offset, not replayed wholesale. Changed variables are diffed against the previous step. Pinned rows sort to the top. Gutter dots are clickable and the breakpoint jumps honour them.

Faked — do not read as a claim

No Python runs. The trace was generated in JavaScript from the same Euler integration the program describes, so the numbers are right but nothing was traced by sys.settrace.

Frames are drawn to a canvas rather than rasterised by matplotlib, so this says nothing about the real cost of draw() + savefig — the estimate assumes 10–40 ms each, and that is the number to measure first.

The chrome is a facsimile: no Ace, no real tabs, one file. Arrow-key adjudication between the panel and the editor — a real design question — cannot be shown here, because there is no editor to lose focus to.

Swap in your own program

The trace is generated from one function at the top of the script. Replacing the projectile integration with a loop from an actual assignment is a few lines, and it is what settles the capture policy for real.

Open questions this specimen is meant to settle

Each one is cheaper to answer by clicking than by discussing.

  1. Does the pill belong in the tab bar at all? It is docked there by default here. Try dragging it over the plot, or to the bottom-left, and see which reads better.
  2. Should the watch window dock under the panel, or pin to a corner? Under the panel it follows the drag, which is tidy until the panel is near the bottom edge.
  3. Value only, or the full trajectory? The sparklines cost about a day. They are also the thing no live debugger can do.
  4. Autoplay speed: five detents (⅕, ½, 1, 2, 4 steps/sec) rather than a continuous slider. Cycle the pill’s speed chip to feel whether five is enough.
  5. Does DEBUG over a bug icon read as “step through my program” to someone who has never used a debugger? That is the whole discoverability bet.
